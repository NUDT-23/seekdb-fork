## 一、题目背景
本地知识库与 AI 应用需要保存文档及向量，根据业务条件检索相似内容，并在数据变化时保持检索结果正确。一个可用的向量数据库不仅要“搜索得快”，还需要可靠的存储、明确的查询语义，以及提交、回滚和故障后的数据一致性。

本题要求实现一个轻量向量数据库 MiniVectorDB。选手在剩余比赛期间自主安排开发进度，完成存储、SQL 执行、向量索引、事务和恢复能力。最终作品应能在统一环境下接收查询、持久化数据，并通过正确性和资源约束测试。

## 二、题目内容
### 2.1 实现范围
限定为单机、单进程、单客户端连接，同一时刻最多一个显式事务。不要求分布式执行、多客户端并发控制或完整 SQL 标准支持。

| 模块 | 必须支持的能力 |
| --- | --- |
| 表结构 | CREATE TABLE；BIGINT、VARCHAR(n)、VECTOR(n)；一个 BIGINT 主键，每表最多一个向量列 |
| 数据操作 | INSERT、SELECT、UPDATE、DELETE；多行 INSERT；按主键或条件更新、删除 |
| 条件查询 | 普通列投影、SELECT *、比较运算符 =、<、<=、>、>=、AND、ORDER BY、LIMIT |
| 向量检索 | L2_DISTANCE、精确 TopK、带普通列过滤的 TopK；近似索引要求以统一题包为准 |
| 持久化 | 保存表定义和数据；正常关闭与重启后内容一致 |
| 事务 | BEGIN、COMMIT、ROLLBACK；事务内读到自己的修改；表数据与向量检索一致 |
| 恢复 | 进程异常退出后恢复；已确认提交的数据不丢，未提交事务不能部分生效 |


本题不要求 NULL、JOIN、聚合、子查询、ALTER TABLE、外键、嵌套事务或主键更新。不支持的语句须返回约定错误，不能静默执行为其他含义。

主键不可重复。VARCHAR 长度按 Unicode 字符数计算，字符串比较按 Unicode 码点顺序，不做语言相关排序。向量为固定维度 float32 数组，输入必须是可表示为有限 float32 的数值，拒绝 NaN、Infinity、维度不符及转换溢出。距离按存储后的向量计算，输出允许统一的浮点误差。

允许使用通用文件、序列化、数学及 SQL 解析库。存储、查询执行、向量索引和事务核心须自行实现，不得使用 SQLite、RocksDB 等现成存储或数据库引擎，也不得调用 Faiss、VSAG、HNSWlib 等现成向量索引库代执行。组织方可提供统一解析辅助代码，具体依赖范围随题包公布。提包会放出部分mysqltest测试例子，可以参考[https://github.com/oceanbase/seekdb/tree/2026-competition-round2/mysqltest](https://github.com/oceanbase/seekdb/tree/2026-competition-round2/mysqltest)。

### 2.2 SQL 与向量检索示例
以下为本题约定的 SQL 子集，完整语法和错误码随公开题包发布：

```sql
CREATE TABLE docs (
    id BIGINT PRIMARY KEY,
    category VARCHAR(32),
    content VARCHAR(1024),
    embedding VECTOR(4)
);

INSERT INTO docs VALUES
    (1, 'database', '事务与恢复', '[1, 0, 0, 0]'),
    (2, 'database', '向量索引',   '[0, 1, 0, 0]'),
    (3, 'travel',   '旅行攻略',   '[0, 0, 1, 0]');

SELECT id, content,
       L2_DISTANCE(embedding, '[0.9, 0.1, 0, 0]') AS distance
FROM docs
WHERE category = 'database'
ORDER BY distance
LIMIT 2;

BEGIN;
UPDATE docs SET embedding = '[0.8, 0.2, 0, 0]' WHERE id = 1;
DELETE FROM docs WHERE id = 2;
ROLLBACK;
```

L2_DISTANCE 返回欧氏距离。过滤后的 TopK 必须在满足 WHERE 条件的记录集合内计算，不能先在全表取 K 条再过滤。结果不足 K 条时返回全部符合条件的记录；距离相同时按主键升序排列。普通 ORDER BY 的并列项也按主键升序排列，未指定 ORDER BY 的结果按集合比较。

精确与近似检索通过测试驱动约定的模式参数显式区分，默认 `exact`，具体传递方式以题包为准。即使建立了近似索引，exact 模式仍须返回精确结果。近似模式使用 `ann`，针对向量 TopK 查询生效。

进阶部分支持 `CREATE VECTOR INDEX index_name ON table_name(vector_column)`。索引算法自行选择，不强制 HNSW；创建后新增、更新和删除的记录必须正确反映到检索结果中。

### 2.3 存储与事务语义
数据和恢复所需文件统一写入 `/data`。每个正式用例从独立的数据目录开始，重启与恢复测试复用该目录。正式测试包含数据量超过内存限额的场景，不能依靠全量载入内存通过所有存储测试。

未显式 BEGIN 时，成功的数据修改语句按自动提交处理。显式事务内的查询和向量检索须看见当前事务已完成的修改。语句失败时，该语句不能留下部分修改，显式事务中之前成功的语句仍可继续提交或回滚。

ROLLBACK 后，记录内容、可见记录集合和向量检索均恢复至事务前状态。提交成功响应发出前，必须完成约定持久化；重启不能丢失已经确认提交的修改。

不限定日志或事务实现方案。向量索引可从持久化记录重建，但重建完成前不得报告数据库就绪，重建成本计入恢复时间与资源限制。

### 2.4 得分机制
总分 **80 分**，按第 3 章的测试方法依次完成 MySQL case 功能准入、性能 benchmark 和 Agent prompt 评价。功能测试不单独计分；性能与 Agent prompt 各占 40 分，分别排名后换算得分。

| 评测环节 | 测试方法与计分依据 | 计入总分 |
| --- | --- | ---: |
| MySQL case 功能准入 | 配套测试驱动通过 stdin/stdout 执行 SQL，校验 SQL、存储、向量检索、事务、恢复与资源约束；全部正式用例通过后才具备计分资格，详见第 3.2 节 | 不单独计分 |
| 小型性能 benchmark | 对批量写入和向量 TopK 查询测量耗时 T、磁盘 I/O B、峰值内存 M，按综合性能指标独立排名，详见第 3.3 节 | 最高 40 分 |
| Agent prompt 评价 | 对问题理解与自主拆解、技术理解与迁移、独立验证与质疑、实验与反馈迭代、取舍与反思五个维度，累计独立证据实例得分；原始评价分不设上限，独立排名，详见第 3.4 节 | 最高 40 分 |


**1. 功能准入**

MySQL case 的每个用例须全部断言通过，且全部正式用例均通过。任一用例错误、崩溃、超时或资源超限，本次提交总分为 0，性能与 Agent prompt 均不进入计分和排名。不按用例通过比例给部分分，公开样例通过不能替代正式准入结果。

**2. 性能排名与得分**

写入和查询分别使用对应基线，将 T、B、M 转换为效率比，经第 3.3.3 节的 f(R) = R / (1 + R) 归一化后，按耗时 60%、I/O 20%、内存 20% 合成单项指标：

**E_写入或查询 = 0.6 × f(R_T) + 0.2 × f(R_B) + 0.2 × f(R_M)**

**E = (E_写入 + 2 × E_查询) / 3**

资源统计范围、平滑常量及基线口径均按第 3.3 节执行。三个有效测量轮次各自计算 E，取中位数并四舍五入保留六位小数，再按从高到低排名。E 仅用于排序，不直接作为得分。

写入和查询的正确性、持久性及资源限制均须满足；查询的有过滤、无过滤两组平均 Recall@10 均须达到 0.95。任一轮校验失败或超出硬性限制，性能项为 0 分且不占性能榜名次。

设有效性能排名为 r_perf（从 1 开始）：

**S_perf = max(40 − 0.5 × (r_perf − 1), 0)**

**3. Agent prompt 排名与得分**

采用 `agent-learning-evidence-v3-unbounded` 规则。五个维度按不重复的独立证据实例累加，每个实例按 0.5、1、1.5、2 分四档取最高适用档位；维度和原始总分均不设固定上限。对同一提交材料独立评审三次，各维度取三次评价的中位数后相加，得到原始评价分 `agent_prompt_score`，按该值从高到低独立排名。原始评价分仅用于排序，不直接计入总分，不设置源码静态扫描评分项。证据不足或评审分歧达到复核阈值时，先完成复核再生成有效分数，详见第 3.4 节。

设有效 Agent prompt 排名为 r_prompt（从 1 开始）：

**S_prompt = max(40 − 0.5 × (r_prompt − 1), 0)**

未提交材料、材料无法读取或没有有效学习材料时，本项为 0 分且不占评价榜名次；平台读取或评审服务故障按平台故障处理。

**4. 总分、并列与异常处理**

**MySQL case 未全部通过：S_total = 0。**

**MySQL case 全部通过：S_total = S_perf + S_prompt。**

通过功能准入后，两项成绩独立有效：性能评测无效仅将性能项记为 0，仍可获得有效的 Agent prompt 得分；Agent prompt 材料无效仅将该项记为 0，仍可获得有效的性能得分。平台故障对同一版本按重测规则处理，不作为选手测试失败。

两榜均采用竞赛排名：并列占用对应名次，后续名次跳过，例如 1、1、3。性能并列按保留六位小数后的 E 判断，Agent prompt 并列按原始评价分判断；并列者获得相同的该项排名分。每项第 1 名 40 分，第 2 名 39.5 分，第 3 名 39 分，第 80 名 0.5 分，第 81 名及以后为 0 分。

例如，功能准入通过、性能第 2 名、Agent prompt 第 3 名时，总分为 39.5 + 39 = **78.5 分**；若性能评测无效而 Agent prompt 第 3 名，则总分为 0 + 39 = **39 分**。

**5. 最终参评版本**

两项成绩必须对应同一次提交锁定的代码版本和 `conversation.json`，不拼接不同提交的成绩。每位选手在截止前从自己的正式提交中指定一个最终参评版本；未指定时，默认采用最近一次 MySQL case 全部通过的正式提交，没有通过版本则总分为 0。

每位选手仅以最终参评版本参与两榜排序，每榜至多占一个名次；不满足该榜准入或有效性要求的版本不占名次。比赛期间榜单为暂定结果，截止后按所有最终参评版本统一排序、结算，不能沿用历史榜单中的最高分。

## 三、测试方法与提测标准
### 3.1 统一运行环境
开发语言和本地操作系统不限，正式运行环境统一为 Linux x86_64 容器。选手提交 Dockerfile，由平台构建并锁定镜像；正式执行时禁止联网，依赖须在构建阶段安装完成并锁定版本。

容器启动后直接以前台方式运行数据库程序，通过标准输入（stdin）接收 MySQL 测试驱动提供的 SQL，通过标准输出（stdout）返回查询结果和执行状态。程序保持运行，支持同一进程内连续执行多条语句及事务，不启动网络监听服务。

SQL 的语句边界、结果集格式、错误码、就绪标识、精确／近似模式切换及正常退出方式，统一遵循 `2026-competition-round2` 分支配套测试驱动和题包约定，不再采用此前示例中的 JSON 请求／响应封装。日志及调试信息写入标准错误（stderr），不得混入标准输出中的评测结果。

程序须及时刷新标准输出缓冲区，避免测试驱动因等待结果而超时。正常关闭时回滚未提交事务并完成必要落盘；异常恢复测试直接强制终止进程，重启时复用 /data 数据目录。正常关闭信号或命令以题包为准。

运行环境、基础镜像、可用依赖、CPU、内存、磁盘、启动及查询超时、数据规模、向量维度和 K 的范围，须在首日开始前随题包冻结发布，赛中不临时增加语言或环境限制。预检与正式评测采用同一运行协议。

### 3.2 MySQL case 功能测试（计分准入条件）
本题的 MySQL case 指采用 mysqltest 风格组织的 SQL 测试脚本与预期结果文件。组织方提供配套测试驱动，通过第 3.1 节的 stdin/stdout 接口发送 SQL 并统一比较输出，不通过 TCP 端口连接选手程序。向量语法、重启和强制终止等操作由题包及测试驱动定义，不能直接使用 MySQL 的行为代替本题语义。

功能测试覆盖基础 SQL、持久化存储、向量检索与索引维护、事务和崩溃恢复。正式题包中的全部用例均须通过；任何一个用例出现错误、崩溃、超时或资源超限，均视为本次准入未通过，总分为 0，不进入性能排名和 Agent prompt 计分。

一个用例的全部断言通过才算通过。各用例独立准备数据，公开样例用于本地验证，不能代替正式用例的全部通过结果。平台反馈用例通过情况和失败类别，不按通过比例给部分分；平台故障按重测规则处理。

| 测试类别 | 验收方法 |
| --- | --- |
| SQL 与存储 | 使用确定性数据和操作序列，对照参考执行器检查结果、错误、记录数量与重启后状态 |
| 精确检索 | 对过滤后的集合暴力计算真值，核对距离、TopK、主键及排序 |
| 近似检索 | 检查返回 ID 有效、无重复、满足过滤条件、对应当前可见记录，并计算 Recall@K |
| 索引维护 | 交错执行建索引、插入、向量更新和删除，验证结果与当前记录一致 |
| 事务 | 对比提交、回滚和语句失败后的参考状态，分别验证普通查询与向量检索 |
| 恢复 | 强制终止后保留 /data，重启并核对提交状态；在恢复途中再次终止，检查重复恢复 |
| 资源 | 限制 CPU、内存、磁盘与时间，检查大于内存预算的数据处理和恢复行为 |


崩溃模型限定为进程被强制终止，不模拟断电、磁盘损坏或文件被外部篡改。已经返回 COMMIT 成功的事务必须保留；未发出提交请求的事务必须回滚；发出提交请求但未收到成功响应的事务，允许完整生效或完整不生效，不能部分生效。自动提交语句适用相同的确认规则。

近似检索的真值也在满足过滤条件的集合中计算。若集合大小为 N，Recall@K 的分母为 min(K, N)；空集合须返回空结果，不参与召回率平均。并列距离使用统一的主键规则产生真值。索引或性能优化不得放宽过滤与事务正确性。

### 3.3 小型性能 benchmark（40 分）
仅 MySQL case 全部通过的最终参评版本可以进入性能评测。综合执行耗时、磁盘 I/O 和峰值内存计算排序指标，再按名次换算为 40 分制成绩。

采用小规模、单客户端负载：默认 10,000 条记录、128 维向量、1,000 条 TopK 查询，K = 10，其中一半查询带普通列等值过滤。数据分布和生成方法公开，正式数据使用未公开随机种子，禁止预存答案。数据规模、内存预算及索引准备上限经赛前试跑统一冻结。

#### 3.3.1 项目与权重
| 性能项目 | 耗时权重 | I/O 权重 | 内存权重 | 项目总权重 |
| --- | ---: | ---: | ---: | ---: |
| 批量写入 | 20% | 6⅔% | 6⅔% | 33⅓% |
| 向量 TopK 查询 | 40% | 13⅓% | 13⅓% | 66⅔% |
| **合计** | **60%** | **20%** | **20%** | **100%** |


权重以第 3.3.3 节的精确公式为准，仅用于确定性能排名，不直接作为分数相加。

批量写入从空表开始，每批 100 条写入并提交；耗时包含全部批次请求、结果输出及完成持久化所需时间。向量查询在数据装载和索引准备后执行，耗时包含全部查询请求处理和结果输出。两项均使用平台测量的端到端时间，不能由选手程序自行上报成绩。

查询允许 exact 或 ann 模式，在提交配置中固定。所有查询均须返回数量正确、无重复且符合过滤条件的记录，距离须对应当前记录；无过滤和有过滤两组的平均 Recall@10 均须达到 0.95。真值按第 3.2 节规则生成。

写入和查询两个项目的配套正确性检查必须全部通过，且未超过 CPU、内存、磁盘容量、I/O 带宽和运行时间限制，才生成有效的综合性能指标。任何项目失败，本次性能分为 0，不占性能榜名次；若 MySQL case 已全部通过，仍可获得 Agent prompt 分。写入须核对记录内容、数量及重启后的持久性，不能通过省略落盘换取分数。

#### 3.3.2 资源统计口径
每轮使用独立容器、独立 cgroup 和独立数据目录。性能计分运行与事后的正确性检查分开，检查产生的开销不计入性能成绩。

| 指标 | 定义 | 统计范围 |
| --- | --- | --- |
| T：耗时 | 平台记录的墙钟时间 | 写入为全部批次执行与持久化；查询为正式查询序列，不含统一预热 |
| B：磁盘 I/O | 专用数据设备上物理读取与写入字节数之和 | 从数据库启动、数据装载、索引准备、预热至测量结束及相关写回完成 |
| M：峰值内存 | 整个数据库容器及其子进程的峰值内存占用 | 与 B 相同的完整运行过程，包含索引构建峰值和文件页缓存 |


查询的索引构建、装载和预热虽不计入 T，但其 I/O 和内存开销计入 B、M，并受准备时间上限约束，避免将高资源成本全部转移到计时前。数据库的数据、日志、索引及临时文件统一位于受统计的 /data，不能转移到未计量的目录或外部服务。

平台采用 Linux cgroup v2 统计：以数据设备的 io.stat 中 rbytes、wbytes 增量计算 B，以 memory.peak 记录 M；内存按容器整体统计，包含页缓存，不能只看单个进程的 RSS。禁用 swap，评测机须验证文件系统的 cgroup 写回归属正常，且所有存储路径均在计量范围内。指标定义参考 [Linux cgroup v2 官方文档](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)。

每轮采用相同的冷启动、缓存初始化和预热流程；数据缓存由平台在隔离评测环境中统一准备，不由选手自行选择冷热状态。结束后保留 cgroup，完成相关文件同步并收集写回数据，再结束统计，不能将后台写盘延迟到统计窗口之外。镜像构建、评测驱动和事后校验不计入选手资源消耗。

基线和选手在相同硬件、CPU 配额、内存限额、磁盘及 I/O 带宽配置下各运行三轮。选手每轮计算综合性能指标，取三轮指标的中位数用于排名，不拼接不同轮次中最好的耗时、I/O 或内存数据。任一轮正确性失败或超出硬性限制，本次性能分为 0、不进入性能榜；平台故障则按平台重测规则处理。

#### 3.3.3 综合性能指标与排名
对写入和查询分别确定固定基线指标 T_base、B_base、M_base，基线各指标取三轮测量的中位数。参考实现满足相同正确性和持久化要求，查询采用精确扫描。

分别计算效率比：

+ R_T = (T_base + ε_T) / (T + ε_T)
+ R_B = (B_base + ε_B) / (B + ε_B)
+ R_M = (M_base + ε_M) / (M + ε_M)

平滑常量为 ε_T = 1 毫秒、ε_B = 1 MiB、ε_M = 1 MiB，用于避免除零和小数值噪声；计算前统一单位。令 f(R) = R / (1 + R)，写入和查询使用各自的效率比：

**E_写入 = 0.6 × f(R_T) + 0.2 × f(R_B) + 0.2 × f(R_M)**

**E_查询 = 0.6 × f(R_T) + 0.2 × f(R_B) + 0.2 × f(R_M)**

**综合性能指标 E = (E_写入 + 2 × E_查询) / 3**

E 仅用于排序，不直接计入总分。三轮 E 取中位数后四舍五入保留六位小数，按从高到低排列；保留六位后相同的指标并列，采用竞赛排名，例如 1、1、3，并列选手获得相同分数。

设排名为 r，从 1 开始：

**性能得分 = max(40 − 0.5 × (r − 1), 0)**

| 性能排名 | 性能得分 |
| ---: | ---: |
| 1 | 40 |
| 2 | 39.5 |
| 3 | 39 |
| 80 | 0.5 |
| 81 及以后 | 0 |


每位选手仅以最终参评版本参与一次排序。未通过 MySQL case 或性能评测无效的版本不占名次。榜单同时展示综合指标、耗时、I/O、峰值内存、排名及得分，最终名次以截止后的统一结果为准。

参考实现、基线测量值、资源配置、统计工具、缓存流程及准备和执行时间上限须在比赛开始前公布并冻结。采集不可用或基线异常按平台故障处理，不能将缺失指标视为 0 开销。

### 3.4 Agent prompt 评价与排名（40 分）
MySQL case 全部通过后，由评测 Agent 分析选手随该次提交上传到指定分支的 Agent prompt 材料 `conversation.json`。本项采用 `agent-learning-evidence-v3-unbounded`，评价对话中可核对的学生理解、验证和改进表现，不对源码进行静态扫描评分。

原始评价分 `agent_prompt_score` 不设固定上限；本节标题的 40 分指独立排名后折算的赛事得分，不是原始评价分的上限。原始分与性能指标分别输出；排名和赛事总分按第 2.4 节另行结算。

#### 3.4.1 评价对象与维度
评审只读取本次提交的单个 `conversation.json`。实际使用的 prompt、必要上下文、Agent 交互记录、实验结果及复盘均须包含在这个 JSON 文件内；不会自动读取仓库其他文件、外部链接或平台运行日志来补充学习证据。只给学生自身有证据支持的贡献计分：Agent 自动给出的优秀规划、技术解释、代码或修复，不直接证明学生理解；日志本身也不证明学生能够解释和使用结果。

| 评价维度 | 评价依据 |
| --- | --- |
| 问题理解与自主拆解 | 学生解释约束、识别关键难点，并有依据地拆解或调整任务；只罗列功能要求不等于理解 |
| 技术理解与迁移 | 学生用自己的解释说明机制、预测行为，并在新场景应用和验证 |
| 独立验证与质疑 | 学生设计独立验证、反例或交叉检查，识别 Agent 建议中的错误或适用边界 |
| 实验与反馈迭代 | 学生参与假设、实验、结果解释、修正和复测，形成可核对的闭环 |
| 取舍与反思 | 学生结合测量结果解释方案代价、失败原因、适用条件与局限 |


不按对话数量、篇幅、调用次数、模型品牌或术语复杂程度加分。表达简短或没有反驳 Agent 不自动扣分，关键在于是否存在独立理解与验证的证据。

#### 3.4.2 独立证据实例与分档
每个不同的问题、实验或修正链作为一个独立实例（unit），选择最相关的一个维度，只计一次。每个实例只取最高适用档位，不将规划、验证、修正和迁移阶段重复累加。

| 单个实例得分 | 必须具备的证据 |
| ---: | --- |
| 0.5 | 学生提出具体问题、预测或验证方案，但没有实际结果 |
| 1 | 学生参与验证，并有实际验证结果 |
| 1.5 | 学生解释结果、据此修正方案并复测，形成完整证据链 |
| 2 | 在同一实例中迁移到新场景，完成验证，并结合结果分析局限 |


没有有效实例时，该维度为 0，报告须引用支持缺失或未执行判断的材料。泛泛的“继续”“帮我优化”“运行一下”或技术名词清单不自动构成实例。

各维度的单轮分数为其有效实例得分之和，维度和原始总分均不封顶。只有规划时，每个独立实例最多 0.5 分；多个真正独立的方案可以累计，不再采用旧版“每维最多 0.5、总分最多 2.5”的限制。此规则不是按条目计数：拆分同一方案、换一种措辞、重复记录或重复测试，均不能增加分数。

例如：两个独立实例分别满足“验证有结果”和“修正后复测”，对应 1 + 1.5 = 2.5 分；若它们实际上属于同一条修正链，只取最高适用档位 1.5 分。

#### 3.4.3 证据引用与去重
每个实例须给出评分理由，并分开提供：

+ `student_evidence`：学生自身贡献的原文位置与片段。
+ `result_evidence`：实际结果的原文位置与片段。高于 0.5 分必须提供；0.5 分档必须为空。

学生贡献与实际结果不能用相同片段代替，也不能用 Agent 的未来计划代替实际结果。引用必须定位到 `conversation.json` 内的字符串字段，包含 RFC6901 JSON pointer 和不超过 240 字符的精确原文。可在 JSON 内保留原始记录编号与版本关联，便于核对，但仅提供外部路径或链接不能代替实际证据内容。

程序校验规则版本、引用可定位性、原文匹配、计分档位、重复原文及维度加和。同一证据不得跨实例或跨维度重复得分。语义上是否属于同一问题或修正链，仍由评审判断，不能通过换词绕过去重。

合成材料只用于评测流程联调，须明确标注，不作为真人学习效果证据。完整材料明确没有执行或反馈时，可按实际证据计 0；材料截断、缺失或完整性无法确认时，不武断判 0，应标记证据不足并复核。

#### 3.4.4 三轮评审、聚合与复核
组织方统一固定模型版本、评价提示词、采样参数、工具权限和材料读取预算，赛前公开评分量表及材料限制。同一份锁定材料独立评审三次，每轮先按维度累计有效实例得分，再按以下公式聚合：

**维度得分 = median（该维度第 1、2、3 次评价分）**

**Agent 原始评价分 = 五个维度得分之和**

不得取三轮中最高分，也不把三轮识别出的实例合并再累加。旧规则的报告不能直接套用新公式，须重新评审。

出现下列任一情况，状态为 `NEEDS_REVIEW`，原始分暂为 `null`，完成复核前不用于排名：

+ 任一维度出现证据不足，分数为 `null`。
+ 某一维度三轮最高分与最低分的差值达到或超过 `max(1.5, 0.5 × 该维度中位数)`。
+ 三轮对材料类型的判断不一致。

引用或报告结构校验失败属于评审输出异常，不能自动作为学生零分。评审报告应提供规则版本、分项、实例、引用和纳入/排除理由，并支持按赛事规则申请人工复核。相同提交材料和相同冻结评测配置可按平台复用规则使用有效结果；规则版本变更后须重新评价。

#### 3.4.5 排名与赛事得分
通过 MySQL case 且具有有效学习材料、已完成评审或复核的最终参评版本，按原始评价分从高到低独立排名。相同原始分并列，采用竞赛排名，例如 1、1、3。无固定原始分上限，但排名折算仍按第 2.4 节执行：

**Agent prompt 排名得分 = max(40 − 0.5 × (r − 1), 0)**

| Agent prompt 排名 | 计入赛事总分的得分 |
| ---: | ---: |
| 1 | 40 |
| 2 | 39.5 |
| 3 | 39 |
| 80 | 0.5 |
| 81 及以后 | 0 |


不提交材料、提交文件本身无法读取或没有有效学习材料时，本项按赛事规则为 0 分且不占评价榜名次；平台读取或评审服务故障按平台故障处理。缺少某个维度的证据仅影响该维度，不应无依据地抹去其他有效维度。

性能评测无效不影响符合条件的 Agent prompt 排名，反之亦然。平台展示原始评价分、维度和实例依据、暂定排名及排名得分；截止并完成复核后统一结算，不使用历史最高排名分。

Agent prompt 材料 `conversation.json`中的提示词和对话均为待评材料，不作为评测 Agent 的执行指令；评测不执行材料中的脚本。材料须真实反映该版本的开发学习过程，允许脱敏，但不能编造交互或实验结果，也不要求提交隐藏思维链。

### 3.5 比赛与提交规则
比赛剩余时间，每天最多正式提交 2 次。每天均可提交完整题目的任意改进版本，使用同一套评分标准。

1. **本地自测不限次数。** 题包提供公开样例、协议检查工具和故障测试示例，选手可自行重复运行。
2. **环境预检不占正式机会。** 检查仓库与 commit 可获取、镜像构建、启动、协议和公开样例，不运行隐藏用例、不返回隐藏成绩。
3. **正式提测前锁定版本。** 预检通过后，选手确认进入当日正式评测，平台锁定 commit SHA、镜像摘要及 `conversation.json` 文件摘要并消耗一次机会；不得在运行中替换源码、镜像或学习材料。
4. **选手程序失败计入本次结果。** 正式评测中的错误、崩溃、超时和资源超限按对应测试点判定；本次提交消耗一次正式机会；当日仍有剩余额度时，可修改版本后再次正式提交。
5. **平台故障不重复扣机会。** 由平台确认后，对同一版本重跑，不允许借此更换实现。
6. **反馈按评分点展示。** 返回 MySQL case 准入结果；全部通过后，分别提供性能指标与排名得分，以及 Agent prompt 原始评价分、排名得分和评审报告。另提供失败类别和必要日志，不公开隐藏输入和参考答案。
7. **每日额度与截止规则。** 每日提交额度按赛事公布的统一时区和时间窗口计算，未使用的额度不结转。某天未提交不会额外扣分，也不影响已有版本的参评资格和后续日期的提交资格；比赛结束后停止接收正式提交。

### 4.2.1 Dockerfile 与启动示例
下面以 Ubuntu 24.04 为基础镜像，使用 stdin/stdout 与 MySQL 测试驱动交互，不需要暴露或映射端口。示例中的程序名和数据目录参数按选手实际实现调整。

```dockerfile
FROM ubuntu:24.04

WORKDIR /app

# 容器封装示例；正式提交须补齐从源码构建的步骤
COPY --chmod=755 minivectordb /app/minivectordb

RUN mkdir -p /data
VOLUME ["/data"]

ENTRYPOINT ["/app/minivectordb"]
CMD ["--data-dir", "/data"]
```

构建镜像：

```bash
docker build -t minivectordb:latest .
```

前台启动并保持标准输入打开：

```bash
docker run --rm -i \
  -v minivectordb-data:/data \
  --cpus=2 \
  --memory=2g \
  minivectordb:latest
```

测试驱动通过进程管道连接容器的 stdin/stdout，stderr 单独收集日志。使用 `-i`，不使用后台运行参数 `-d` 或分配 TTY 的 `-t`，以保持输入输出通道适合自动评测。无需 EXPOSE、端口映射或 host／port 启动参数。

数据库持久化文件写入 /data。示例的 2 核 CPU、2 GiB 内存仅用于本地演示，正式资源限额以题包为准。

上述 COPY 二进制方式用于说明容器封装；正式提交须包含源码，并在 Dockerfile 中补齐从源码构建的步骤，或采用多阶段构建，不能依赖选手本地预编译且未提供构建流程的文件。程序须兼容 Linux x86_64，所需运行库也须安装到镜像内，基础镜像及依赖版本按题包要求锁定。

### 4.4 Agent prompt 材料：单个 conversation.json
将单个 `conversation.json` 与源码、Dockerfile 一起提交到 `2026-competition-round2` 分支，并纳入同一次 commit。当前评测入口默认读取仓库中的 `agent/conversation.json`；组织方如调整位置，须统一配置材料路径。无需提交额外的对话目录或 ZIP，也不接受用 Markdown、文本文件代替此 JSON 输入。

文件须采用 UTF-8 编码、合法 JSON，顶层为对象，大小不超过 128 KiB。超限时拒绝评审，不静默截断。输入不应包含重复 JSON 键或 NaN、Infinity 等非标准 JSON 数值。

评审只将这个 JSON 的内容作为选手学习材料，不会自动搜索其他文件。需评分的学生贡献与验证结果均应直接写入 JSON：

+ 真实用户 prompt 和必要上下文，明确区分学生、Agent 和工具结果的来源。
+ 对话中的分析、提问调整、实验及反馈，保留判断过程所需的前后文与记录编号。
+ 实际验证结果、学生对结果的解释、修正复测及反思；未执行的内容应明确标为计划。
+ 材料范围、脱敏说明或缺失说明。仅用于联调的合成材料须标记 `synthetic: true`。

内部字段可组织为 `user_prompts`、`conversations`、`experiments`、`retrospective`、`limitations` 等，但这些只是建议字段，当前读取程序不强制该业务字段结构，也不要求每个字段都存在。需要引用的关键证据应保存在字符串字段中，供评审通过 JSON pointer 和原文片段定位。例如，学生发言可位于 `/conversations/0/content`，实际结果可位于 `/experiments/0/output`；记录编号、来源和时间可使用相邻字段补充。
